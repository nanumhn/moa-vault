## 무엇이 문제였나 — 표면과 실제가 달랐다
형 지시로 보류 기사를 열어보다 시작됐는데, 진단이 **세 번 바뀌었다**. 매번 더 깊었다:
```
1차 진단   "원문을 안 읽는다"        → 틀림. enrichSources가 런타임에 원문을 가져온다
2차 진단   "근거 540자에 1,600자 요구" → 맞지만 얕음
3차(실제)  그 540자의 65%가 회사 주소·저작권 푸터였다. 실제 기사는 150자
           ★그런데 로그엔 "원문 1/1 확보(540자) 성공"으로 찍혔다
```
최악 사례(`blog-post_27`)는 확보된 747자가 **KBS 사이트 메뉴와 무관한 기사 제목들**이었다("읽어주기 기능은 크롬기반…", "이 대통령 브라질 도착", 기자 이름). 그 위에서 1,600자를 요구하니 모델이 NYT 인용 15건과 정부기관 발언을 지어냈다.

**★핵심 구조: 실패가 성공으로 계기판에 찍힌다.** 같은 날 같은 유형이 3건 나왔다 — 원문 추출 실패→"확보 성공" / 근거 없음→게이트 "통과" / 블로그 본문 증발→빌드 성공. 아예 실패하면 로그라도 남는데 이 구조는 아무도 모른다.

## ★게이트 방어 (현재) — 실제로 막는 건 4번이 아니라 2·3번이다
1. 출처 줄 — 문구가 아니라 출처 명시 여부
2. **수치 근거 대조** — 원문에 없는 숫자 차단 (외부 참고링크 2건 이상이면 검수자 확인으로 완화)
3. **인용 근거 대조** — 원문에 없는 발언 차단
4. 근거 부족 차단 — 원문 400자 미만이면 수치·인용 있는 글은 발행 불가

**★내가 처음에 잘못 기록했던 것:** "MIN_EVIDENCE=400을 추가해서 막았다"고 썼는데 **틀렸다.**
사고 기사 ①은 원문이 **747자**라 400을 넘어 길이 게이트를 그냥 통과한다. 실제로 막은 건 **2·3번 대조**다.

즉 이번 수정의 본질은 *"길이 게이트를 추가한 것"*이 아니라 **"원문이 없거나 얇을 때 대조를 스킵하던 경로를 없애 대조가 항상 실행되게 한 것"**이다. 무관한 747자와 대조하니 인용 15건이 전부 불일치로 잡혔다.

**재현 검증 완료** [확인]: 당시 원문(KBS 메뉴·무관 기사 제목)으로 두 기사를 다시 돌리니
```
① 이란전 출구전략  FAIL — 원문에 없는 인용 15건
② EU 구글 제재     FAIL — 원문에 없는 수치 4건 + 인용 2건
```
