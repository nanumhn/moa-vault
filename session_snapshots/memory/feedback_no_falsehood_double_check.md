**형 지시 (2026-07-28, 아투 게이트 강도 논의 중):**
> "멈추지 않고 수정해서 간다!!!"
> "**거짓은 담지 않는다!!!**"
> "**더블체크 필수**"

## 두 원칙은 함께 간다
| | |
|---|---|
| **멈추지 않는다** | 정시 발행은 고객과의 약속. 게이트에 걸려도 발행을 세우지 말고 고쳐서 간다 |
| **거짓은 안 담는다** | 그렇다고 거짓을 싣고 가지도 않는다. **못 쓰면 그 자리를 비운다 — 지어내서 채우지 않는다** |
| **더블체크** | 만든 사람 말고 다른 눈이 한 번 더. **"했다"가 아니라 "실제로 그렇게 됐다"를 확인** |

이 셋을 동시에 만족시키는 설계가 정답이다. "멈추거나 거짓을 싣거나" 둘 중 하나를 고르는 건 설계 실패다.

**How to apply:** 게이트가 잡으면 ①그 문장만 재생성 ②그래도 남으면 삭제하고 진행 ③빈자리는 **원문에 실제로 있는 사실로만** 채우거나 그냥 비운다. 그리고 **목표는 "잘 빼는 것"이 아니라 "뺄 게 없는 글"** — 생성 프롬프트를 먼저 고친다. 제거는 안전망일 뿐이고, 제거가 자주 발동하면 그 자체가 실패 신호다.

## ★더블체크 — 완료 보고는 재조회 값으로만
같은 날 "했다"만 보고 "됐다"를 안 봐서 **세 번** 틀렸다:
1. 쇼츠 검수 **9/9 통과** 보고 → 실제 첫 프레임은 좌우로 잘려 있었다(`firstFrameBranded`를 손으로 true 입력)
2. **"GitHub에 수정본 push 완료"** → 원본을 조회하니 오류가 그대로였다(push 성공 ≠ 내용 변경)
3. 쇼츠 새 검사가 **"통과"** → 자막을 열어보니 창작 문장이 그대로였다(블로그 본문과 대조해서 통과한 것)

**규칙:** 완료 판정의 근거는 **실행 성공 응답이 아니라 결과를 다시 조회한 값**이다.
- API 200/204 = 전송됨이지 반영됨이 아니다
- git push 성공 = 내용이 바뀐 게 아니다
- 게이트 통과 = 대조 기준이 옳았을 때만 의미가 있다 (기준부터 의심하라)
- 공개물은 **소스와 라이브를 각각** 확인한다. 한 단계만 보면 오늘 2번 같은 오보가 난다
