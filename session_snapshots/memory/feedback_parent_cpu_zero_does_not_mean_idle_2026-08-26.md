**2026-08-26 11:12, 클로가 형과 덱스가 보는 스레드에 "덱스가 놀고 있습니다"라고 올렸다. 틀렸다.**

## 무엇을 쟀고 무엇을 놓쳤나

쟀던 것: `codex.exe` (pid 13308) 하나. **4초간 CPU 증가 0.00초** → *"놀고 있음"* 이라고 단정.

**실제로는 자식들이 일하고 있었다** `[확인]`:
```
vitest.mjs (pid 5964)                     ← 테스트 실행 중. 재측정하는 사이에 끝나서 사라졌다
next dev (16344 / 21904 / 18352)
.next/dev/cache/turbopack/*.sst           ← 11:12:27 · 11:13:17 에 계속 쓰이는 중
codex-code-mode-host.exe (25060)
codex-command-runner-0.149.1.exe (3292)
```

**코덱스·앤티그래비티 같은 CLI 도구는 실제 작업을 자식 프로세스에 위임한다.** 부모는 대기만 하므로 **부모 CPU는 항상 0에 가깝다.**

## ★이게 특히 나쁜 이유 — 내가 남에게 시킨 규칙이었다

같은 날 **09:43에 클로가 제나에게** 이렇게 지시했다:
> *"**pid만 보고 판정 금지.** 반드시 이름·실행경로까지 대조해라."*
> *"판정 1순위는 **응답 바이트가 돌아오나**다. 한 가지 지표로 단정하지 마라."*

**그리고 1시간 반 뒤에 클로가 정확히 그 실수를 했다.** 남에게 시킨 검사를 자기에겐 면제했다 — [[feedback_pinocchio_clo_dont_assert_without_checking]] 의 *"그걸 누가 정하니?"* 와 같은 모양이다.

## 하마터면 어떻게 될 뻔했나

형이 그때 이렇게 지시하신 상태였다: *"진행하는 거 없으면 재시작하고, 있으면 완료될 때까지 대기하고 이후에 재시작한다."*
**"놀고 있음"을 그대로 믿고 재시작했으면 돌아가던 테스트를 통째로 죽일 뻔했다.** 측정 오류가 실제 손실이 될 자리였다.

## 그래서 "일하는 중"은 이렇게 판정한다

1. **자식 프로세스까지 합쳐서 재라.** `Get-CimInstance Win32_Process -Filter "ParentProcessId=<pid>"` 로 자식을 찾고 그것들의 CPU도 본다.
2. **작업 산출물이 늘고 있나 봐라** — 로그·캐시·출력 파일의 `LastWriteTime`. 위 사례는 `.next` 캐시가 결정적 증거였다.
3. **가장 확실한 건 물어보는 것이다** — (a)작업 중 (b)승인창이 화면에 안 떴다 (c)막혔다 (d)끝났는데 답이 안 갔다. **넷 중 하나 고르게 하면 침묵도 진단이 된다.** 실제로 덱스가 (d), 제나가 (b)로 드러났다.
4. ★**한 지표로 단정하지 마라.** 프로세스 존재·CPU·창 제목·로그 증분은 **전부 각각 거짓말을 한다.** 관련: [[reference_window_title_is_not_an_identifier_2026-08-26]] · [[reference_relaying_results_does_not_unblock_approval_2026-08-26]]

**보고할 때는 "놀고 있다"가 아니라 "내가 잰 범위에서는 활동이 안 보인다"라고 써라.** 범위를 밝히면 틀려도 남이 잡을 수 있다 — [[feedback_pass_count_must_state_scope]]
