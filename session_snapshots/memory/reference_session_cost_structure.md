**사용 한도는 계정 공용(5시간 롤링)이다. 서브에이전트별 개별 한도가 아니다.** 에러 문구가 "session limit"이라 오해하기 쉽다. 직원 여러 명을 동시에 오래 굴리면 메인 세션 몫까지 같이 태운다.

## 실측 [확인 — 2026-07-27, 세션 로그 `~/.claude/projects/<proj>/<sid>.jsonl` 집계]
```
요청 672회 / 누적 3억 2,339만 토큰
  cache read  3억 1,859만  ← 98.5%. 컨텍스트 재읽기 누적
  output          45만
세션 종료 시점 컨텍스트 크기  약 77만 토큰
```

## 비용 구조 — 이게 핵심
요청 1회당 **그때까지의 컨텍스트 전체를 다시 읽는다.** 세션이 길어질수록 요청당 비용이 선형 증가한다.
```
세션 초반 컨텍스트 5만  → 워치독 1회 5만
길어진 뒤    77만       → 워치독 1회 77만   (15배)
```
**5분 워치독 = 하루 288회.** 컨텍스트 77만이면 **형 메시지가 하나도 없어도 하루 2.2억 토큰**을 태운다. 2026-07-26 한도 소진의 주범은 서브에이전트가 아니라 이것이었다.

## 대응
1. **세션 리셋 주기를 짧게** — 효과 최대. 주2회면 컨텍스트가 100만 근처까지 자라고, 매일이면 15~20만에서 유지된다. ⚠️ `MoaSessionReset`(수·일 04:00)이 **Disabled 상태로 발견됨**(2026-07-26). 켜져 있었으면 한도가 안 찼을 것. **형 결정 대기 중**(활성화 + 매일로 변경)
2. **워치독 시간대별 차등** — 적용 완료(2026-07-27). 주간 08~23시 5분 / 새벽 00~07시 20분. `session_bootstrap.md`에도 반영해 다음 세션이 자동으로 이렇게 등록한다
3. (미착수) 워치독을 세션 밖으로 빼고 **새 메시지가 있을 때만** 세션을 깨우기 — 지금은 메시지가 없어도 매번 깨워 확인한다. 근본 해결이지만 구현 필요

## 스케줄 충돌 점검 [확인]
```
04:00  세션 리셋
09:05  GSC 리포트      ← 리셋 후 5시간. 새 세션 cron 재등록 시간 충분
09/13/17  헬스체크
07:30(월) 주간 전략 리포트  ← 리셋 후 3.5시간
```
04:00 리셋은 다른 일정과 겹치지 않는다. 시각 변경 불필요.

## ★★ 진짜 주범은 "턴 수"가 아니라 "턴 안의 도구호출 스텝 수" (2026-08-05 실측)
워치독 사이클 수보다 **작업이 몰린 턴 하나**가 훨씬 크게 비용을 태운다. 같은 세션 실측: 외부 워치독 스크립트를 만드는 작업 턴 하나(59단계: 파일읽기·스크립트작성·에러디버깅·테스트·스케줄러등록·메모리기록)가 **1,281만 토큰**을 혼자 먹었다 — 조용한 워치독 사이클 1회(20~25만)의 50배 이상. 이유: 턴 안의 도구 호출 스텝마다 그 시점까지 쌓인 컨텍스트 전체를 다시 읽으므로, **한 턴 안에서 스텝 수가 많을수록 그 안에서 선형이 아니라 거의 스텝수×컨텍스트크기로 늘어난다.** 형이 "890만인데 갑자기 3237만"이라고 물어본 게 이 케이스 — 버그 아니고 정직한 결과. **함의**: 워치독 빈도를 아무리 줄여도 무거운 멀티스텝 작업(코드 리팩토링·여러 파일 편집·디버깅 세션)을 세션 후반부에 하면 그게 총 비용의 대부분을 차지한다 — 세션을 자주 리셋해서 그런 무거운 작업이 "컨텍스트 작을 때" 일어나게 하는 게 워치독 최적화보다 효과가 크다.

## ★서브에이전트 위임 = 무거운 멀티스텝 작업의 진짜 절감책 (2026-08-05, 형 질문으로 정리)
서브에이전트(Agent 도구)는 메인 세션과 별개로 **거의 0에 가까운 새 맥락에서 시작**한다. 그래서 위 "59단계=1281만 토큰"([[project_discord_external_watchdog_2026-08-05]]) 같은 무거운 멀티스텝 작업을 메인 세션에서 직접 하면 스텝마다 이미 커진 메인 맥락을 다시 읽어야 하지만, 같은 작업을 서브에이전트에 위임하면 그 서브에이전트는 자기 작은 맥락만 반복해서 읽으므로 훨씬 싸다 — 끝나고 결과만 메인 세션으로 편입된다. 추가로 `Agent(model:'fable')`로 위임하면 별도 사용량 계정(주간 한도와 분리)으로 잡힌다([[reference_local_hardware_spec]] 인접 항목, CLAUDE.md 변경이력 07-28 "무거운 작업의 Fable 위임" 참고 — 단, 분리 계정 여부는 화면 관측일 뿐 실측 1회 필요, 미착수). **원칙: 스크립트 작성·디버깅·여러 파일 편집처럼 무거운 멀티스텝 작업은 메인 세션에서 직접 하지 말고 서브에이전트로 위임할 것.** ★A/B 실측 비교는 아직 안 해봄(다음 기회에 같은 작업으로 검증할 것 — 정확한 절감폭 미확정, 방향성만 확인).

## ★★"토큰 수"≠"비용" — raw count와 할인 비용을 혼동하지 말 것 (2026-08-05, 형이 공식 문서로 지적)
Anthropic 프롬프트 캐싱 공식 문서: 캐시읽기(cache_read_input_tokens)는 정가의 **0.1배**(90% 할인), 캐시쓰기는 1.25~2배. 이 세션 대화에서 지금까지 "N만 토큰"으로 보고해온 숫자는 전부 **순수 토큰 개수(raw count)**이지 할인 반영된 비용이 아니다 — 즉 캐시읽기가 97%인 지금 상황에서, 실제 "비용"은 보고한 토큰 수보다 훨씬 작을 가능성이 있다(캐시읽기 부분만 1/10로 쳐지므로).
**핵심 미확인 사항**: Claude Code의 세션/주간 사용한도가 (a)순수 토큰 개수 기준인지 (b)캐시 할인까지 반영한 비용 기준인지 — 이걸 모르면 "토큰 N만"이 실제로 한도에 얼마나 위협적인지 판단 불가. (b)라면 오늘 보고한 경고성 숫자들은 실제 위험도를 과대평가한 것일 수 있다. 세션 내부에서 한도 계산 로직 접근 불가 → 형에게 `/usage` 화면 제공 요청함(재차 요청, 아직 미제공).

## 한도 %를 사전에 알 수 있나 → 없다 [확인]
- `/usage` 슬래시 명령은 있지만 사용자가 터미널에 직접 입력하는 것이라 에이전트가 호출 불가
- 로컬 JSONL에 토큰은 기록되지만 **한도 값이 없어** %를 계산할 수 없다
- 우회안: 형이 `/usage` 화면을 1회 제공하면 그 시점 집계값과 대응시켜 **환산 계수**를 만들 수 있다 → 이후 로그 집계로 80/90/95% 경고 가능. **형 제공 대기 중(2026-08-05 재요청)**
