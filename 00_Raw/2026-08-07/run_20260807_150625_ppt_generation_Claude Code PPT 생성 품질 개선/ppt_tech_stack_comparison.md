# PPT 생성 기술 스택 비교

작성: 이도연(프론트엔드) · 보완: 정도현(COO, 검수 반려 6·7번 반영)

## 후보 비교표

| 방식 | 디자인 자유도 | 편집 가능한 .pptx | 구현 난이도 | Claude Code 적합도 | 비고 |
|---|---|---|---|---|---|
| python-pptx | 중간 | 가능 (텍스트·표·차트 모두 네이티브) | 중간 | 좋음 | 정교한 비주얼은 코드량이 많아진다 |
| pptxgenjs | 중간 | 가능 (네이티브) | 중간 | 좋음 | Node 기반, 차트 API가 더 풍부 |
| Marp / Reveal.js | 높음 | **불가능** (HTML·PDF 출력) | 낮음 | 부적합 | 최종 산출물 요건(.pptx)을 못 맞춤 |
| HTML렌더→이미지→pptx | 높음 | 컨테이너만 가능 — **슬라이드 안 텍스트는 수정 불가** | 중간 | 보조 수단으로 적합 | 장식 슬라이드 한정으로 쓰면 유효 |

`Claude Code 적합도`는 "코드로 자동 생성하기 좋은가"를 뜻한다. Marp/Reveal.js는 도구가 나빠서가 아니라 편집 가능한 .pptx라는 요건을 못 채워 부적합이다.

## 권고 1안

- **선택: python-pptx 단독 기본 + HTML/CSS 렌더 이미지를 장식 슬라이드에만 부분 적용**
- 이유 3가지:
  1. 최종 산출물 요건이 "고객이 수정할 수 있는 .pptx"다. 텍스트·표·차트를 네이티브 개체로 넣는 python-pptx만 이 요건을 충족한다.
  2. 밋밋함의 원인은 도구가 아니라 규격의 부재였다. 디자인 시스템(컬러·타이포·그리드)을 코드로 강제하면 python-pptx만으로도 충분히 정돈된 결과가 나온다.
  3. 화려함이 꼭 필요한 표지·섹션 구분은 편집 대상이 아니다. 그 두 종류만 렌더 이미지로 얹으면 편집 가능성을 잃지 않고 자유도를 얻는다.

### 네이티브와 렌더 이미지의 경계 (구현 시 이 한 줄이 기준)

**고객이 문구를 고칠 가능성이 있는 슬라이드는 python-pptx 네이티브로, 고칠 일이 없는 장식 슬라이드(표지·섹션 구분)만 HTML/CSS 렌더 이미지로 만든다.**

본문·데이터·단가·사례 슬라이드는 예외 없이 네이티브다. 이미지로 얹으면 고객사명 하나 고치려 해도 우리에게 다시 요청해야 한다.

## 대안 (1안이 막힐 때)

- **pptxgenjs**
- 이유:
  1. python-pptx의 차트 API로 표현이 안 되는 복합 차트가 필요해지면 pptxgenjs가 더 넓다.
  2. 파이프라인을 Node로 통일해야 할 사정이 생기면 이쪽으로 옮긴다.
  3. 같은 OOXML을 쓰므로 산출물 요건(.pptx 편집 가능)은 그대로 유지된다.

Marp / Reveal.js는 대안에 넣지 않는다. 위 비교표에서 `.pptx` 산출 불가로 이미 배제한 안이며, 대안으로 되살리면 결론이 다시 열린다.

## 생성 파이프라인 단계

1. **입력** — 주제와 자료를 마크다운으로 받는다. 고객사명·업종·요구사항이 필드로 들어온다.
2. **원고 생성** — 마크다운을 슬라이드 단위로 쪼개고 각 장이 답할 질문과 레이아웃 유형을 결정한다.
3. **에셋 준비** — 표지·섹션 구분은 HTML/CSS로 렌더해 PNG로 뽑고, 배경 이미지는 이미지 생성 또는 무료 스톡에서 조달한다.
4. **조립** — python-pptx로 슬라이드를 만든다. 장식 슬라이드는 PNG를 전면 배치하고, 나머지는 텍스트·표·차트를 네이티브 개체로 넣는다.
5. **검사·출력** — 품질 게이트를 돌려 P0 위반이 없으면 `.pptx`로 저장한다.

## Claude Code 실행 명령 예시

```bash
python build_deck.py --brief brief.md --template proposal --out 제안서.pptx
```

## 예상 리스크 3개와 대응

1. **렌더 이미지가 본문까지 침범해 편집 불가 슬라이드가 늘어난다** → 위 경계 규정을 코드로 강제한다. 레이아웃 유형이 표지·섹션 구분일 때만 이미지 배치 함수를 타도록 분기한다.
2. **python-pptx로 디자인을 흉내 내다 코드가 비대해진다** → 도형 조합은 좌측 컬러 바·오버레이 같은 값싼 장치로 제한하고, 그 이상이 필요하면 렌더 이미지 쪽으로 넘긴다.
3. **폰트가 고객 PC에 없어 레이아웃이 깨진다** → 제목·본문 폰트를 문서에 임베드하거나, 임베드가 어려우면 시스템 기본 폰트로 대체했을 때의 줄바꿈을 미리 확인한다.
