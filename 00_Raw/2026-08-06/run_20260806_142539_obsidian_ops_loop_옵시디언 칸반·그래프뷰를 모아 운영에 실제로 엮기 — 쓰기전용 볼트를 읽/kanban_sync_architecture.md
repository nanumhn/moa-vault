# 칸반同步架构

## 决定摘要
- 真实来源：前端标记（status）作为卡的状态。
- 写主：开发本部负责人负责写入`TODO.Kanban.md`。
- 同步方式：通过dataview自动聚合和显示。

## 数据流
```
任务发生 → (更新前端标记) → (dataview自动收集) → (更新卡状态) → git提交
```

## 文件写权限
| 文件路径 | 写主 | 写入时机 | 读取主体 |
|---|---|---|---|
| `TODO.Kanban.md` | 开发本部负责人 | 每次任务开始时 | dataview、系统各部分 |

## 状态字段定义
| status 值 | 卡列 | 含义 | 转移条件 |
|---|---|---|---|
| todo | 待办事项 | 任务待处理 | ... |
| waiting | 等待中 | 需等待资源或审批 | ... |
| doing | 进行中 | 正在执行中 | ... |
| done | 完成 | 任务完成 | ... |
| hold | 暂停 | 任务暂停 | ... |
| blocked | 被阻塞 | 因外部因素停滞 | ... |

## 文件冲突处理
- 当开发本部负责人在打开Obsidian时程序尝试写入`TODO.Kanban.md`，程序会先备份文件。
- 然后以只读方式更改文件并执行操作，最后提交git变更。

## 失败恢复
| 失败 | 检测 | 恢复 |
|---|---|---|
| 写入失败 | 通过git状态检测 | 使用最新备份回滚 |

## 核心风险3个及应对措施
1. 写入冲突 → 程序先备份再尝试写入，确保数据一致性。
2. 数据丢失 → git提交记录帮助恢复。
3. dataview错误聚合 → 验证dataview查询逻辑正确性。
