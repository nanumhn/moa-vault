# 칸반 동기화 아키텍처

## 결정 요약 (3줄)
- 진실의 원천: 프론트매터 `status` 필드로 둔다. 이는 칸반 보드와 대시보드가 그로부터 파생되기 때문.
- 쓰기 주체: archive-head-haru(기록관리본부장)가 매일 일지를 작성할 때, 그리고 qa-lead-jian이 프로젝트 허브 노트를 업데이트할 때.
- 반영 방식: dataview 자동 집계를 사용하여 칸반 보드와 대시보드가 실시간으로 갱신되도록 한다.

## 데이터 흐름
```
작업 발생 → (파일/필드) 프론트매터 status 필드 변경 → (처리) dataview 쿼리로 반영 → (표시) 칸반 보드와 대시보드 갱신 → git commit
```

## 파일별 쓰기 권한
| 파일 경로 | 쓰기 주체 | 쓰기 시점 | 읽는 주체 |
|---|---|---|---|
| 01 Dashboard/TODO.Kanban.md | archive-head-haru(기록관리본부장) | 일지 작성시 | 모든 사용자 |
| 02 Projects/k-saju.md, 아투.md, 덱스제나.md, 쇼츠.md, 애드센스.md | qa-lead-jian | 프로젝트 허브 노트 업데이트 시 | archive-head-haru(기록관리본부장) |
| 70 Record/YYYY-MM-DD.md | archive-head-haru(기록관리본부장) | 일지 작성시 | qa-lead-jian, k-saju |

## 상태 필드 정의
| status 값 | 칸반 컬럼 | 의미 | 전이 조건 |
|---|---|---|---|
| todo | 할 일 | 현재 진행되지 않는 작업 | 형성 중인 프로젝트 또는 개인 건 |
| waiting | 대기 중 | 완료될 예정이지만 아직 시작되지 않은 작업 | 기대되는 업데이트, 검토, 의존성 |
| doing | 진행 중 | 현재 진행 중인 작업 | 프로젝트 허브 노트의 진행 상태를 반영 |
| done | 완료 | 완전히 완료된 작업 | 프론트매터 `status: done`으로 변경 |
| hold | 보류 | 일시적으로 보류된 작업 | 추가 정보 필요, 의사결정 대기 |
| blocked | 차단됨 | 작업 진행을 방해하는 문제로 잠정 중지 | 의존성 부족, 리소스 부족 |

## 파일 충돌 대응
- 형이 옵시디언을 열어둔 채 프로그램이 쓰면, 백업을 먼저 생성한 후 원자적인 쓰기를 수행한다. 이후 git 기준 복구 절차를 통해 최신 상태로 되돌린다.
  - 백업: `git stash` 명령어 사용
  - 원자적 쓰기: `git commit --allow-empty`
  - 복구: `git reset --hard HEAD@{1}`

## 실패 복구
| 실패 | 감지 | 복구 |
|---|---|---|
| 칸반 보드 또는 대시보드가 일관성이 없는 상태로 변경된다. | dataview 쿼리가 실패하거나 git commit이 제대로 이루어지지 않을 경우, 모아 운영팀에 알림을 보내고, git 이력으로 복구한다. | `git checkout .` 명령어 사용하여 파일을 복구하고, `git pull --rebase`로 최신 상태를 가져온다. |

## 핵심 리스크 3개와 대응
1. 프론트매터 `status` 필드가 올바르게 업데이트되지 않을 경우: archive-head-haru(기록관리본부장)는 일지를 작성할 때마다 카드의 상태를 검토하고, dataview 쿼리를 통해 자동화된 대시보드와 칸반 보드가 일치하는지 확인한다.
2. git commit이 제대로 이루어져 있지 않을 경우: 백업과 원자적인 쓰기를 통해 안정적으로 복구할 수 있도록 절차를 마련하고, 모아 운영팀에 알림을 보내는 시스템을 구축한다.
3. 칸반 보드 또는 대시보드가 일관성이 없는 상태로 변경되는 경우: dataview 쿼리가 실패하거나 git commit이 제대로 이루어지지 않을 경우, 모아 운영팀에 알림을 보내고, git 이력으로 복구한다.
