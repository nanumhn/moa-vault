# 엑셀 파일 동기화 옵션 비교

## 5가지 시나리오 정의
| 시나리오 | 한 줄 정의 | 대표 도구/원리 |
| :--- | :--- | :--- |
| **1. 파일 레벨 싱크** | 전체 파일을 통째로 교체하며, 최신 타임스탬프를 기준으로 병합. | Dropbox, 기본 FTP 동기화 |
| **2. 셀/레인지 Diffing** | 변경된 특정 셀(Cell)이나 범위(Range)만 식별하여 전송하고 반영. | Google Sheets의 일부 기능 |
| **3. DB 트랜잭션 싱크 (추천)** | 모든 데이터를 중앙 집중식 데이터베이스에 저장하고, 애플리케이션 계층에서 동기화 로직을 제어. | API 게이트웨이 + 트랜잭션 로그 |
| **4. CRDT 기반 싱크** | 충돌 발생 시 데이터의 수학적 속성을 이용해 자동으로 병합하여 무결성 확보. | Conflict-free Replicated Data Types |
| **5. LWW (Last Writer Wins)** | 가장 마지막에 쓰인 사용자의 값이 다른 모든 값을 덮어쓰는 방식. | 단순 타임스탬프 기반 동기화 |

## 각 옵션 trade-off 매트릭스
| 옵션 | 구현 난이도 | 양방향 지원 | 충돌 처리 메커니즘 | 데이터 무결성 | 추천 케이스 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **파일 레벨** | 하 | O | 매우 취약 (덮어쓰기) | 낮음 | 단순 읽기 전용 배포, PoC 초기 검증. |
| **셀/레인지 Diffing** | 중 | O | 특정 범위 충돌은 감지 가능하나 복잡함. | 중간 | 데이터 변경 영역이 명확하고 제한적인 경우. |
| **DB 트랜잭션 싱크** | 상 | O | 중앙 제어층(Transaction Layer)에서 강제적 검증 및 병합 로직 구현. | 높음 | 필수 비즈니스 데이터를 다루는 모든 서비스 (권장). |
| **CRDT 기반** | 최상 | O | 수학적으로 충돌이 발생하지 않도록 설계. | 매우 높음 | 분산 시스템의 극한 환경, 높은 이론적 완성도 요구 시. |
| **LWW** | 하 | O | 가장 최근에 접근한 값으로 무조건 덮어쓰기. | 최저 | 단일 사용자 작업이나 데이터 손실을 감수할 수 있는 경우. |

## 의사결정 트리 (Decision Flow)
**START: 동기화 아키텍처 설계**

1.  **[질문] 데이터의 중요도와 무결성 요구 수준이 높은가?**
    *   YES $\rightarrow$ 2로 이동.
    *   NO $\rightarrow$ LWW 또는 파일 레벨 싱크 (제한적 사용).

2.  **[질문] 동시 편집 가능성이 발생하며, 충돌 시 데이터 손실이 치명적인가?**
    *   YES $\rightarrow$ **DB 트랜잭션 싱크 아키텍처 필수.** (중앙 집중식 제어층 도입)
        *   -> [세부 확인] 복잡한 병합 로직(CRDT 급)까지 필요한가?
            *   YES $\rightarrow$ CRDT 고려 (리소스 할당 최상).
            *   NO $\rightarrow$ **'Conflict Log 기록 + 중앙 트랜잭션 관리'**로 범위를 제한.

3.  **[질문] 동기화 주체가 단일하거나, 변경 빈도가 매우 낮은가?**
    *   YES $\rightarrow$ 셀/레인지 Diffing 또는 파일 레벨 싱크 고려 가능.
    *   NO $\rightarrow$ 반드시 DB 트랜잭션 싱크를 채택해야 함.

## 결론 — '대부분의 한국 SMB가 처음 시도할 때 권장하는 1개 옵션'과 근거
**옵션:** 중앙 집중식 트랜잭션 관리 계층 기반의 데이터베이스 동기화 (DB Transaction Sync)

**근거:** 초기 단계에서는 기술적 완벽성보다 '예측 가능성(Predictability)'이 우선입니다. DB 트랜잭션 레이어를 도입하면, 복잡한 충돌을 앱 레벨에서 제어하고 실패 시나리오를 명확히 기록할 수 있어 운영 안정성을 확보하는 것이 가장 효율적입니다.
