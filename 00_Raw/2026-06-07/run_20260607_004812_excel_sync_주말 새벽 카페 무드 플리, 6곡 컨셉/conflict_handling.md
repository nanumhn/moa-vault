# 엑셀 동기화 충돌·실패 처리

## 가장 위험한 실패 케이스 3개
| 발생 조건 | 증상 | 방어 코드 위치 | 사용자 알림 정책 |
| :--- | :--- | :--- | :--- |
| **Race Condition** (동시 쓰기) | 두 클라이언트가 같은 셀을 다른 값으로 수정 후 동기화 시, 데이터 손실 또는 예측 불가능한 값이 반영됨. | 중앙 트랜잭션 레이어의 Lock/Versioning 로직. `Optimistic Locking` 적용 필수. | "경고: [셀 이름]에 대한 동시 편집이 감지되었습니다. 수동 병합을 진행해 주십시오." (P0) |
| **Partial Sync Failure** (부분 전송 실패) | 네트워크 불안정으로 인해 전체 데이터 셋 중 일부만 성공적으로 전송되고, 클라이언트와 서버의 상태 플래그가 불일치함. | Webhook 리스너 및 트랜잭션 커밋(Commit) 직전의 State Check Logic. 모든 변경 로그는 원자적 단위로 처리되어야 함. | "오류: 데이터 동기화 중 오류가 발생했습니다. 실패한 블록을 재시도할 수 있도록 안내합니다." (P1) |
| **Schema Drift** (스키마 불일치) | 한 사용자가 특정 열(Column)의 데이터 타입을 변경하거나, 새로운 필드를 추가했을 때, 다른 클라이언트가 해당 구조를 인식하지 못함. | 백엔드 API 게이트웨이 레벨에서 강제하는 스키마 검증 및 타입 체크 로직. 모든 요청은 OpenAPI 정의서 기반으로 유효성 검사해야 함. | "경고: 데이터 구조 변경이 감지되었습니다. 서비스 사용을 위해 [필요 조치]를 진행해 주세요." (P1) |

## 충돌 정책 비교
*   **LWW (Last-Write-Wins):** 구현 난이도는 낮으나, 가장 위험합니다. 누가 어떤 데이터를 덮어썼는지에 대한 *재현 가능한 실패 시나리오*가 너무 많아 P0 이슈로 간주해야 합니다. 데이터 손실의 원인 추적이 불가능해 수동 감사(Audit) 작업이 필요합니다.
*   **CRDT (Conflict-free Replicated Data Type):** 이론적으로는 완벽하지만, 현재 MVP 단계에서 요구되는 테스트 범위와 시스템 오버헤드가 지나칩니다. 기능적 완성도에만 초점을 맞추기에는 리소스 배분이 비효율적입니다.
*   **수동 머지 (Manual Merge) + Conflict Log:** V1.0의 가장 현실적인 방안입니다. 충돌 발생 시 강제로 사용자에게 알리고
