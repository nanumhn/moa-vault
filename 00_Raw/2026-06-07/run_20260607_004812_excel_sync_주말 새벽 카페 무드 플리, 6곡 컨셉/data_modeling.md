# 엑셀 동기화 데이터 모델링

## 동기화 단위 — 시트 / 행 / 셀 / 명명된 범위 비교
데이터 무결성과 운영 효율성을 최우선으로 고려할 때, '행(Row)' 레벨을 최소한의 동기화 단위로 설정하는 것을 권고합니다. 셀(Cell) 단위는 트랜잭션 추적 및 충돌 관리(Conflict Resolution)가 지나치게 복잡해지며, 명명된 범위 역시 구조 변경에 취약합니다.

*   **권장 단위:** **행 (Row)**
*   **이유:** 모든 행을 하나의 원자적 기록(Atomic Record)으로 정의하고, 해당 행의 고유 식별자(Unique ID)를 기준으로 데이터 전송 및 버전 관리가 가능합니다. 변경된 필드(Field)만 트랜잭션 계층을 통해 감지하여 전송하는 구조가 오버헤드를 최소화할 수 있습니다.

## 3개 대표 사용 케이스별 권고 단위
| 케이스 | 권고 동기화 단위 | 충돌 위험도 | 운영 부담 (관리 난이도) |
| :--- | :--- | :--- | :--- |
| **재무 데이터** | 행 레벨 (전체 트랜잭션 기록) | 중하 (데이터 변동 빈도가 낮음) | 중. 승인(Approval) 및 감사 추적 로직 필수 구현. |
| **프로젝트 트래커** | 행 + 필드별 변경 로그 (Conflict Log) | 상 (다수의 동시 편집 가능성 높음) | 상. 중앙 집중식 트랜잭션 계층을 통한 강제 관리 필요. |
| **설문 응답** | 전체 기록 단위 (Immutable Record) | 최하 (최종 제출 시점의 원본 데이터로 간주) | 하. 읽기 전용(Read-Only) 형태로 정의하여 수정 최소화. |

## 운영자 1명 관리 한계 (파일 수 / 동시 사용자 수)
운영자가 수작업으로 관리할 수 있는 시스템 범위는 단순히 파일 개수가 아닌 **'데이터 구조의 복잡성'**과 **'일일 트랜잭션 발생 건수(TPS)'**에 의해 제한됩니다.

*   **트랜잭션 한계:** 일일 50건 이상의 기록이 지속적으로 발생하는 경우, 수동 관리는 지연 및 오류 위험이 높아집니다.
*   **사용자 충돌 관리:** 동시 편집자가 3명 이상이고 해당 데이터가 비정형적 필드를 포함할 경우, 시스템적 변경 로그(Change Log)와 승인 절차를 강제하는 것이 필수입니다.

## '동기화 안 해도 되는 데이터' 식별 가이드
다음과 같은 성격의 데이터는 동기화 과정에서 제외하거나, 읽기 전용(Read-Only) API 호출을 통해 데이터를 가져오는 방식을 권장합니다. 이는 트랜잭션 부하를 줄여 아키텍처 안정성을 높이는 데 기여합니다.

1.  **참조 테이블 (Reference Data):** 카테고리명, 사용자 역할 정의 등 변경 빈도가 매우 낮은 마스터 데이터.
2.  **공개 통계/메타 정보:** 전체 조회수 합산, 총 이용자 수와 같이 실시간 집
