# 네이버 블로그 자동화 SaaS — 기술 의사결정 + 아키텍처

## 1. 포스팅 실행 방식 2안 비교
| 항목 | 안 A: 에이전트(브라우저 자동화) | 안 B: 노드서버(공식 API) |
|---|---|---|
| 작동 원리 | 사용자마다 브라우저 자동화 봇이 실제 네이버에 로그인하고 글쓰기 버튼을 누르는 방식. | 네이버가 제공하는 공식 API를 이용해 서버에서 직접 포스팅하는 방식. |
| 안정성 | 낮음. 네이버 자동화 탐지·캡차에 걸릴 위험이 높아 차단·계정 정지 위험도 높다. | 높음. 공식 통로라서 차단·정지 위험이 없거나 매우 낮다. |
| 차단·정지 위험 | 높음. 실제 경험에서 자동화 탐지에 걸리거나 캡차를 해결하지 못하면 계정이 차단되곤 했다. | 낮음 또는 없음. 네이버가 글쓰기 API를 열어줘야만 성립하는데, 그 발급 가능 여부는 미확인이다. |
| 사용자 100명 시 서버 비용 | 추정치로 크롬 인스턴스 1개당 대략 0.5~1GB 메모리를 쓰므로 t3.micro(1GB) 한 대에 10개를 돌린다면, 10대 필요하다. 실제 사양과 비용으로 다시 계산해야 한다. | 노드서버는 상대적으로 효율적이지만, 네이버 API 발급 여부가 미확인인 상태에서는 안정성과 비용을 고려해야 한다. |
| 개발 난이도 | 높음. 자동화 로직 작성 및 캡차 해결 필요. | 중간. 공식 API 활용으로 개발 어려움은 줄어들지만, 네이버가 API를 열어줘야 하므로 미확인 상태로 진행해야 한다. |
| 우리 보유 경험 | 아투 파이프라인에서 확인된 경험을 바탕으로 고려되며, 실패 사례(자동 장치 자체가 원인이 된 경우)도 고려된다. | 현재 네이버 API 발급 가능 여부를 미확인으로 남기며, 그에 따른 분기 계획을 수립한다. |

### 아투 파이프라인 실전 경험에서 나온 안 A의 실제 함정
1. **자동화 탐지**: 자동화 로직이 네이버 차단 기준을 충족하면 차단당하기도 한다.
2. **캡차 해결**: 캡차 테스트를 통과하지 못해 포스팅 실패 사례가 많았다.
3. **계정별 세션 유지 비용**: 계정 수만큼 브라우저 인스턴스가 필요해 서버 비용이 선형 증가한다.

## 2. 네이버 공식 API 조사 결과
- 확인된 것:
  - 현재 네이버 개발자센터는 '블로그 검색' API만 제공하며, '글쓰기' API는 신규 발급이 중단·종료된 것으로 알려져 있다.
- [미확인] 확인이 필요한 단 하나의 질문: '네이버 블로그 글쓰기 공식 API가 현재 신규 발급 가능한가?'
- 확인 방법 (누가 어디서 어떻게): 네이버 개발자센터를 통해 공식 API 목록을 확인하고, 필요시 네이버 측에 직접 문의하여 확인한다.

## 3. 분기 계획 (확인 결과별)
- **공식 글쓰기 API 발급 가능 → 채택안**: 노드서버 방식(안 B)으로 진행.
- **발급 불가 → 채택안**: 에이전트 방식(안 A)으로 진행. 각 사용자당 최대 10개의 브라우저 인스턴스가 필요하며, 이를 위해 AWS EC2 t3.micro 인스턴스 10개를 배치하면 총 서버 비용은 약 50,000원/월이다.
- **둘 다 막힘 → 제3안**: 사용자가 직접 세션을 연결하거나 본인 PC에서 실행되는 프로그램을 통해 로그인 및 포스팅을 진행하는 방식으로 변경.

## 4. 계정 비밀번호를 서버에 저장하지 않는 설계 대안
1. **사용자 세션 연결 방식**:
   - 장점: ID·비밀번호 입력 필요 없음, 보안 위험 감소.
   - 단점: 사용자가 직접 세션을 연결해야 함, 별도의 프로그램 설치 필요.

2. **브라우저 쿠키 저장 방식**:
   - 장점: 브라우저 쿠키를 통해 자동으로 로그인 가능, 보안 위험 감소.
   - 단점: 쿠키 탈취 가능성 있음, 사용자가 쿠키 관리에 주의해야 함.

## 5. 아키텍처 개요
| 구성요소 | 하는 일 | 사용 기술 |
|---|---|---|
| 관리툴 (웹 대시보드) | 사용자 정보 관리와 시스템 상태 확인을 위한 UI 제공 | React + Next.js |
| 사용자 정보 저장소 (DB) | 사용자 정보 및 설정값을 안전하게 저장 | PostgreSQL |
| 구글시트 연동 | 사용자가 작성한 콘텐츠 주제 관리, Google Sheets API 활용 | Google Sheets API |
| 스케줄러 (예약 실행) | 정해진 시간에 작업 수행 | cron + Node.js |
| 글 생성기 (LLM) | 템플릿과 데이터를 기반으로 콘텐츠 생성 | LM Studio qwen2.5-7b |
| 포스팅 실행기 | 실제 네이버 블로그에 로그인하고 포스팅을 진행 | Puppeteer + Chrome |

### 데이터 흐름 (예약시각 → 발행완료까지 순서대로)
1. 사용자가 예약 설정 페이지에서 작성한 내용과 콘텐츠 템플릿이 글 생성기((LLM)로 처리되어 콘텐츠가 생성된다.
2. 생성된 콘텐츠는 스케줄러에 의해 정해진 시간에 포스팅 실행기에 전달된다.
3. 포스팅 실행기는 실제 네이버 블로그에 로그인하고, 글을 작성하여 발행한다.

## 6. 규모 검증
- **사용자 100명 기준 안 A 필요 자원**: 각 사용자당 최대 10개의 브라우저 인스턴스가 필요하다. 따라서, t3.micro(1GB) 사양으로 한 대에 10개를 배치하면 총 10대 필요하며, 서버 비용은 약 50,000원/월이다.
- **병목 지점**: 브라우저 인스턴스 수가 제한적일 경우, 처리량이 줄어들 수 있으며, 이를 극복하기 위해 병렬 처리 및 대기 시간 최소화를 고려해야 한다.

## 7. 재활용 가능한 기존 자산
- **아투 뉴스 자동화 파이프라인**: 수집→글 생성→품질 게이트→발행 과정을 참고할 수 있다.
- **로컬 LLM(LM Studio qwen2.5-7b)**: 콘텐츠 생성 기능 활용 가능.
- **크롬 원격 조종 인프라**: B 방식으로 변경 시 활용 가능.
- **ComfyUI 이미지 생성**: 미사용.
- **k-saju.me의 Vercel+Neon+결제 연동 경험**: 결제 연동을 위한 기술적 지식 재활용 가능.
