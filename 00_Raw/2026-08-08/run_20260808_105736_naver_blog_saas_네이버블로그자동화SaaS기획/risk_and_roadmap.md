# 네이버 블로그 자동화 SaaS — 리스크 + 로드맵

## 치명적 리스크 Top 3
### 리스크 1: 사용자 네이버 계정정보 보관
- 무엇이 위험한가 (보안 / 법 / 약관): 개인정보를 서버에 저장하는 것은 보안 문제와 법적 책임을 떠안게 됩니다.
- 발생 시 영향: 고객의 개인 정보 누출로 인한 법적 대응 요구, 회사의 명예 손상
- 계정정보를 안 갖는 대안 2개:
  - 사용자 본인 PC에서 도는 프로그램을 통해 세션 관리
  - 사용자가 직접 세션을 연결하는 방식으로 로그인 및 포스팅 수행
- 조기 감지 지표: 고객의 보안 불만이나 법적 대응 요구 신호

### 리스크 2: 네이버 저품질 판정 (발행은 되는데 검색에 안 잡힘)
- 왜 발생하는가: 자동으로 생성된 글은 블로그 정책에서 저품질로 분류되어 검색에 노출되지 않습니다.
- 발생 시 영향 (고객 가치 0): 고객이 원하는 검색 노출을 받지 못해 서비스 가치가 제로
- 대응 (품질 기준 / 발행 빈도 / 일 1회 제한이 안전장치인 이유): 품질은 정확하고 유용한 콘텐츠를 생산하며, 일 1회만 자동 포스팅으로 제한하여 검색 알고리즘의 불공정성을 최소화합니다.
- 조기 감지 지표: 고객 피드백에서 저품질 콘텐츠 관련 불만

### 리스크 3: 계정 정지 시 고객 손해 책임
- 우리 책임 범위: 네이버가 계정을 정지한 경우, 그로 인한 모든 손해를 회사가 책임지게 됩니다.
- 약관에 명시할 문구 방향: "회사는 네이버의 정책 변경으로 인한 계정 정지로 인한 손실이나 손해에 대해 책임지지 않습니다."
- 조기 감지 지표: 네이버가 공식적으로 계정 정지 정책을 변경하거나 업데이트하는 신호

## 추가 리스크 (간단히 2개)
### 리스크 4: 캡차 해결 실패
- 무엇이 위험한가: 자동화 탐지로 인해 네이버 차단당할 가능성이 높아져 서비스 중단 위험이 증가
- 발생 시 영향: 포스팅 중단으로 서비스 가치 감소
- 대응 (캡차 해결 방법): 사용자에게 캡차 해결 옵션을 제공하여 자동화를 최소화하고, 실패 시 재시도 기능 추가
- 조기 감지 지표: 자동화 탐지 로그에서의 안정성 관련 문제점

### 리스크 5: 서버 오버로드
- 무엇이 위험한가: 브라우저 인스턴스 수가 늘어날 경우 서버 성능이 저하되어 서비스 중단 위험이 증가
- 발생 시 영향: 사용자 경험 감소, 서비스 불안정성 증가
- 대응 (사용량 관리): 각 사용자당 최대 10개의 브라우저 인스턴스를 설정하여 서버 성능을 안전하게 유지
- 조기 감지 지표: 서버 로그에서의 응답 시간 증가

1. 네이버 공식 글쓰기 API 발급 가능 여부 확인
2. MVP 소프트웨어 배포 전 테스트 결과 승인
3. 최종 가격 플랜 결정

## 이 사업을 접어야 하는 조건 (Kill 기준)
- 네이버 블로그 글쓰기 API 발급 불가능한 경우
- 초기 테스트에서 심각한 보안 문제가 발견되는 경우
- 고객 피드백에서 계속적인 저품질 콘텐츠 관련 불만이 있는 경우
