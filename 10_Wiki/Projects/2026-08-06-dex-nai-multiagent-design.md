OpenAI Codex("덱스")와 Google Gemini/Antigravity("나이")를 디스코드 봇 워커로 붙여, 클로가 지휘자로서 작업을 분배한다. 참고 매뉴얼은 macOS+tmux 전제였지만, 조사 결과 **WSL도 tmux도 없이 윈도우 네이티브로 구현 가능**하다고 확인했다.

## 1. 배경 조사 — 왜 이 방식인가

기존 moa-studio 하네스는 클로(Claude Code) 세션 하나가 Windows Task Scheduler로 상시 구동되고, 클로가 Agent 도구로 여러 전문 서브에이전트(coo-dohyun·cto-seojin 등)를 오케스트레이션하는 구조다. 이 서브에이전트들은 전부 같은 Claude 모델 위에서 돈다.

형이 공유한 매뉴얼은 이와 달리 **모델 자체가 다른 워커**(Codex/GPT, Gemini)를 디스코드 봇으로 붙이는 구조다. 핵심 차이는 "같은 모델의 역할극"이 아니라 "실제로 다른 모델이 일한다"는 점 — 토큰 한도가 분리되고(클로드 한도를 안 씀), 모델별 강점을 쓸 수 있고, 진짜 교차검수(다른 아키텍처의 눈)가 가능하다.

**기술 실현성 조사 결과(2026-08-06, cto-seojin 수행, 웹 확인 기반):**
- Codex CLI — 윈도우 네이티브 지원 공식 확인(`developers.openai.com/codex/windows/windows-sandbox`). WSL 불요. 단, 최초 1회 UAC 대화형 셋업 필요(무인 최초설치 불가).
- Antigravity(제미나이 CLI `agy`) — 윈도우 공식 설치 스크립트 존재, 네이티브 실행파일.
- 브리지 프로그램(오픈소스, 디스코드 REST↔각 CLI 중계, `netwaif/codex-discord`) — Node.js 단일 의존성(discord.js), headless 모드는 tmux 불요. 윈도우에서 문제되는 지점 3곳 확인(§4 참고), 전부 경미한 수정.
- 상시구동 — 우리가 이미 쓰는 방식(Task Scheduler + Hidden PowerShell, `MoaAckBot`·`MoaMcpGuard` 선례)을 그대로 재사용 가능. tmux·launchd 불필요.

## 2. 검토한 접근법

| 후보 | 내용 | 판정 |
|---|---|---|
| **A (채택)** | 매뉴얼 구조를 윈도우 네이티브로 이식 — 별도 디스코드 봇 계정 2개(덱스·나이) + 오픈소스 브리지(윈도우 패치) + Task Scheduler 상시구동 | ✅ 매뉴얼로 검증된 구조, 형이 "각자 이름으로 작업하는" 시각적 구분을 원함 |
| B | 브리지 없이 클로가 직접 Codex/Antigravity CLI를 서브프로세스로 호출(Bash 도구로), 결과만 웹훅으로 "덱스"/"나이" 이름으로 대신 게시 | ❌ 구현은 더 가볍지만, 각 모델이 독립적으로 상시 대기하며 자기 판단으로 일하는 게 아니라 클로가 매번 대신 실행하는 것 — "다른 모델이 일한다"는 원래 목적이 약해짐 |
| C | WSL 안에 macOS 매뉴얼 그대로 이식(tmux 포함) | ❌ 불필요한 우회 — 조사 결과 윈도우 네이티브로 되는데 WSL 계층을 더할 이유 없음 |

**채택 이유:** A가 매뉴얼의 핵심 가치(각 모델이 독립적으로 반응하고 자기 이름으로 게시하는 것)를 보존하면서, 조사로 확인된 윈도우 네이티브 경로를 그대로 쓸 수 있다.

## 4. 역할 분담

- **나이(제미나이)**: 리서치·조사·대량 텍스트 분석. 무료 사용이라 부담 없이 굴림. research-lead-seoyun 영역과 상당 부분 겹침 — 겹치는 작업은 나이로 우선 이관해 클로/리서치본부장 부담을 줄인다.
- **덱스(코덱스)**: 코딩 특화 작업 + cto-seojin 산출물의 독립 교차검수(다른 아키텍처 눈으로 버그를 잡는 목적, 매뉴얼의 `codex-critic` 패턴과 동일).
- **클로**: 지휘자 역할 유지. 작업 배분·검증·형 보고는 지금과 동일.

## 5. 운영 방식

기존 "위임 규칙"([[feedback_autonomy_delegation]]) 그대로 확장한다 — 클로가 판단해서 덱스·나이에게 위임하고, 결과만 형에게 보고. 매뉴얼의 "매 작업 승인 게이트"는 도입하지 않는다(형 확정: "지금처럼 해야지, 클로가 잘 관리하니까"). 단, 정착 초기(첫 1~2주)는 비용이 드는 작업이나 실발행되는 산출물은 결과 직후 형에게 별도로 짚어 보고한다.

## 6. 구현 시 손볼 지점 (조사로 확인된 것만)

1. 브리지의 `agy.mjs` — macOS `sysctl`용 PATH 접미사(`:/usr/sbin:/sbin`)가 윈도우 PATH(`;` 구분자)를 깨뜨림. `process.platform` 가드 1줄 추가.
2. `.env`에 Codex/agy 실행파일 절대경로(`.exe`) 지정 — Node 20.12+의 `spawn EINVAL`(CVE-2024-27980) 회피. 브리지가 이미 `CODEX_BIN`/`AGY_BIN` 오버라이드를 지원하므로 설정만 하면 됨.
3. 브리지의 `scripts/install.sh`(macOS 전용, launchd)는 안 쓰고, 우리 방식(Task Scheduler + Hidden PowerShell, `MoaAckBot` 선례)으로 상시구동 스크립트를 새로 작성.

**공급망 주의**: 브리지 저장소는 개인 1인 프로젝트(스타 1개). 코드 리뷰 후 특정 커밋에 고정해서 쓴다. 그대로 신뢰하지 않는다.
