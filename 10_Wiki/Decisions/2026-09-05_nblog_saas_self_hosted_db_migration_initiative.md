## 1. 배경 및 문제 의식
현재 `nblog-saas` 운영 환경은 AWS Lightsail(도메인 `nblog.nanumn.com`, 서울 리전)에서 웹 서비스를 구동하고, DB는 클라우드 서버리스 관리형인 **Neon PostgreSQL**을 호출하고 있다.
- **리스크 1: 네트워크 지연**: 매 API 요청마다 외부 Neon 서버리스 엔드포인트로 왕복 트래픽이 발생하여 지연이 가중됨.
- **리스크 2: 사용량 급증 시 비용 및 커넥션 한계**: 데이터가 누적되고 활성 블로그/회원이 늘어나면 관리형 DB 비용이 급증함.
- **리스크 3: 대규모 데이터 이전 비용**: 데이터가 수십만~수백만 건으로 커진 뒤 DB를 이전하려면 마이그레이션 다운타임과 무결성 검증 공수가 기하급수적으로 증가함.

---

## 2. 6대 검토 기준 (덱스 정리)
1. **저장 용량 및 확장성**: Lightsail 블록 스토리지 / 전용 인스턴스 볼륨 사이징.
2. **동시 커넥션 및 CPU 부하**: PgBouncer 커넥션 풀링 및 CPU 리소스 최적화.
3. **월 운영 비용**: Neon 관리형 종량 비용 vs Lightsail VPS 고정 비용(월 $10~$20) 비교.
4. **백업/복구 목표 (RPO / RTO)**: 일일 pg_dump 스냅샷 및 장애 시 10분 내 복구 체계.
5. **보안 및 운영 부담**: SSL 인증서, 보안 패치, 방화벽(포트 5432 폐쇄, 로컬 소켓/내부망만 허용).
6. **데이터 무중단 이전 난이도**: 운영 Neon DB -> 자체 DB 이관 시 다운타임 최소화(10분 이내) 절차.

---

## 3. 선제 준비 로드맵
1. **1단계 (005-05 완료 즉시)**: 현재 Neon DB 스키마 및 용량 베이스라인 측정.
2. **2단계**: Lightsail 내 로컬 Docker PostgreSQL 또는 독립 VPS 인스턴스 테스트베드 구성.
3. **3단계**: `pg_dump` -> `pg_restore` 데이터 덤프/이관 스크립트 작성 및 리허설(스테이징 검증).
4. **4단계**: 형 결재 카드(`REQ-...`) 상정 후 안전한 점검 시간대에 `DATABASE_URL` 전환 배포.
